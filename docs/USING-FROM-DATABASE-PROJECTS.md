# Using this repo from other database projects

This repository (**DBDeploymentTool** / package `sql-migration-tools`) is **shared tooling**. It is not a database.

Each SQL Server database lives in its **own** repo. That repo depends on this package, then runs `sql-mig` against its own `Deployments/` and `SchemaModel/`.

```
┌─────────────────────────────────────────┐
│  This repo (install once)               │
│  github.com/nakkavamsi/DBDeploymentTool │
│  pip package: sql-migration-tools       │
│  CLI: sql-mig                           │
└──────────────────┬──────────────────────┘
                   │  pip install
     ┌─────────────┼─────────────┐
     ▼             ▼             ▼
 Databasecode   OrdersDb      InventoryDb
 (sample)       (your repo)   (your repo)
 Deployments/   Deployments/  Deployments/
 SchemaModel/   SchemaModel/  SchemaModel/
 *.sqlproj      *.sqlproj     *.sqlproj
```

Do **not** copy `src/sql_mig/` into each database repo. Install the package and keep schema SQL in the database project.

Command details: [HOWTO.md](HOWTO.md). Internals: [DOCUMENTATION.md](DOCUMENTATION.md).

## Sample project: Databasecode

[nakkavamsi/Databasecode](https://github.com/nakkavamsi/Databasecode) is the reference database project that already uses this tool.

Clone it to see a working layout, sample migrations, MSBuild sync, and CI:

```bash
git clone https://github.com/nakkavamsi/Databasecode.git
cd Databasecode
pip install -r requirements.txt
sql-mig run --list-files
sql-mig sync
dotnet build Databasecode.sqlproj --configuration Release /p:NetCoreBuild=true
```

What Databasecode demonstrates:

| Piece | Role |
|-------|------|
| `Deployments/Migrations/1.0.0` … `2.2.0` | Sample incremental SQL (Customer, Person, svc, play, …) |
| `SchemaModel/` | Generated SSDT model (do not edit) |
| `Databasecode.sqlproj` | `Microsoft.Build.Sql` project; runs `sql-mig sync` before build |
| `requirements.txt` | Installs `sql-migration-tools` |
| `.github/workflows/` | CI: install tools, `sql-mig sync`, dacpac build, `sql-mig run` against SQL Server 2022 |
| `templates/SqlMigrationDatabase` | `dotnet new` / VSIX starter for new database repos (lives in this tooling repo) |

Treat Databasecode as the **consumer**. Treat this repo as the **tool**.

## What each database project must contain

Minimum layout `sql-mig` expects (relative to `--project-root`, default: current directory):

```
MyDatabaseProject/
├── requirements.txt              # depends on this package
├── MyDatabase.sqlproj            # optional but recommended
├── SchemaModel/                  # generated by sql-mig sync
└── Deployments/
    ├── Migrations/               # source of truth
    │   └── 1.0.0/
    │       └── 01_....sql
    ├── pre-deployments/          # optional
    └── Rollback/                 # optional; unused by sql-mig
```

Version folders **must** be `MAJOR.MINOR.PATCH` (`1.0.0`, not `1.0` or `v1.0.0`).

This tools repo never stores those SQL files.

## Wire an existing or new database repo

### 1. Depend on this package

In the **database** repo, `requirements.txt`:

```text
sql-migration-tools @ git+https://github.com/nakkavamsi/DBDeploymentTool.git
```

Install:

```bash
cd MyDatabaseProject
pip install -r requirements.txt
sql-mig --help
```

While developing the CLI next to the database repo:

```text
# requirements.txt — local sibling checkout
sql-migration-tools @ file:///absolute/path/to/sql-migration-tools
```

or:

```bash
pip install -e ../sql-migration-tools
```

### 2. Create folders

```bash
mkdir -p Deployments/Migrations Deployments/pre-deployments Deployments/Rollback/SOFT Deployments/Rollback/FULL SchemaModel
```

### 3. Add migrations (greenfield)

```bash
sql-mig new --version 1.0.0 --name dbo.customer
# edit the generated file, keep -- Migration-Id
sql-mig sync
```

### 4. Or bootstrap from a live database (brownfield)

Export schema-only SQL (SSMS Generate Scripts, SqlPackage, mssql-scripter), then:

```bash
sql-mig bootstrap --input baseline.sql --version 1.0.0 --sync
```

If the target database **already matches** that baseline, skip applying `1.0.0`:

```bash
sql-mig run -S localhost -d MyDb -U sa -C --exclude-version 1.0.0
```

### 5. Hook sync into the SSDT / dacpac build

Copy the pattern from Databasecode’s `Databasecode.sqlproj`:

```xml
<Project Sdk="Microsoft.Build.Sql/2.2.0">
  <PropertyGroup>
    <Name>MyDatabase</Name>
    <DSP>Microsoft.Data.Tools.Schema.Sql.Sql160DatabaseSchemaProvider</DSP>
    <DefaultFileStructure>BySchemaAndSchemaType</DefaultFileStructure>
  </PropertyGroup>

  <!-- Requires: pip install -r requirements.txt -->
  <Target Name="SyncSchemaFromMigrations" BeforeTargets="Build">
    <Exec Command="sql-mig sync --project-root &quot;$(MSBuildProjectDirectory)&quot;" />
  </Target>

  <ItemGroup>
    <Build Remove="Deployments/Migrations/**/*.sql" />
    <Build Remove="Deployments/Rollback/**/*.sql" />
    <Build Remove="Deployments/pre-deployments/**/*.sql" />
    <None Include="Deployments/Migrations/**/*.sql" />
    <None Include="Deployments/Rollback/**/*.sql" />
    <None Include="Deployments/pre-deployments/**" />
  </ItemGroup>
</Project>
```

`Deployments/` must **not** compile into the dacpac. Only `SchemaModel/` should.

Then:

```bash
dotnet build MyDatabase.sqlproj --configuration Release /p:NetCoreBuild=true
```

### 6. Apply to SQL Server

From the database project directory (`sqlcmd` required):

```bash
sql-mig run -S localhost -d MyDb -U sa -C --status
sql-mig run -S localhost -d MyDb -U sa -C
```

Windows integrated auth: `-E` instead of `-U`/`-P`. Prefer `SQLCMDPASSWORD` over `-P` in CI.

## Three ways to start a new database project

### A. Clone the sample (fastest to learn)

```bash
git clone https://github.com/nakkavamsi/Databasecode.git MyNewDb
cd MyNewDb
# rename Databasecode.sqlproj / project Name, replace sample SQL, keep the layout
pip install -r requirements.txt
```

Use this to study migrations and CI. Strip sample `dbo` / `svc` / `play` objects before using it as a real database.

### B. `dotnet new` template from this repo

This tooling repo ships the project template:

```bash
git clone https://github.com/nakkavamsi/DBDeploymentTool.git
cd DBDeploymentTool
dotnet new install ./templates/SqlMigrationDatabase

dotnet new sql-migration-db -n MyCustomerDb -o ../MyCustomerDb
cd ../MyCustomerDb
pip install -r requirements.txt
dotnet build MyCustomerDb.sqlproj --configuration Release /p:NetCoreBuild=true
```

Details: [templates/README.md](../templates/README.md). Visual Studio VSIX: [extensions/README.md](../extensions/README.md).

### C. Empty repo + this CLI (from scratch)

1. Create a git repo with the folder layout above.
2. Add `requirements.txt` pointing at this package.
3. Add a `.sqlproj` with the `sql-mig sync` MSBuild target (or run `sql-mig sync` yourself before `dotnet build`).
4. `sql-mig new` or `sql-mig bootstrap`.

## Daily workflow in a database repo

Always `cd` into the **database** project, not this tools repo.

```bash
cd MyDatabaseProject
pip install -r requirements.txt          # once per machine / CI job

sql-mig new --version 2.3.0 --name dbo.person.add_status
# edit Deployments/Migrations/2.3.0/*.sql

sql-mig sync
dotnet build MyDatabase.sqlproj --configuration Release /p:NetCoreBuild=true

sql-mig run -S localhost -d MyDb -U sa -C --status
sql-mig run -S localhost -d MyDb -U sa -C
```

Optional `python3 scripts/…` wrappers live in **this** repo (`scripts/`). Copy them into a database project only if you still want those command names. New database repos should call `sql-mig` directly.

## CI pattern (copy from Databasecode)

Install this package, then run CLI from the database checkout:

```yaml
- uses: actions/setup-python@v6
  with:
    python-version: "3.x"

- name: Install sql-migration-tools
  run: pip install -r requirements.txt

- name: Validate migrations
  run: sql-mig run --list-files

- name: Sync SchemaModel
  run: sql-mig sync

- name: Build dacpac
  run: dotnet build MyDatabase.sqlproj --configuration Release /p:NetCoreBuild=true

- name: Apply pending migrations
  env:
    SQLCMDPASSWORD: ${{ secrets.DEPLOY_SQL_PASSWORD }}
  run: |
    sql-mig run \
      -S "${{ secrets.DEPLOY_SQL_SERVER }}" \
      -d "${{ secrets.DEPLOY_SQL_DATABASE }}" \
      -U "${{ secrets.DEPLOY_SQL_USER }}" \
      -C
```

Working examples:

- [Databasecode `.github/workflows/build.yml`](https://github.com/nakkavamsi/Databasecode/blob/main/.github/workflows/build.yml)
- [Databasecode `.github/workflows/deploy-migrations.yml`](https://github.com/nakkavamsi/Databasecode/blob/main/.github/workflows/deploy-migrations.yml)

## Optional Cursor hook

This repo ships `.cursor/hooks.json` and `.cursor/hooks/stamp-migration-id.sh`. Cursor project hooks only run in the **database** workspace, so copy them into each database project if you want Agent writes under `Deployments/Migrations/` stamped automatically:

```bash
cp -R .cursor /path/to/MyDatabaseProject/
chmod +x /path/to/MyDatabaseProject/.cursor/hooks/stamp-migration-id.sh
```

The hook calls `python3 -m sql_mig stamp`, so the package must be installed in that environment. It does **not** run when you type and save a file yourself.

`sql-mig new` and `sql-mig sync` also stamp missing IDs, so the hook is optional.

## Checklist for a second (or third) database repo

- [ ] Separate git repo for that database (not a copy of `src/sql_mig`)
- [ ] `requirements.txt` → `sql-migration-tools @ git+https://github.com/nakkavamsi/DBDeploymentTool.git`
- [ ] `Deployments/Migrations/` with semver folders
- [ ] `sql-mig sync` before dacpac build (MSBuild target or CI step)
- [ ] `Build Remove` for `Deployments/**/*.sql` in the `.sqlproj`
- [ ] `sql-mig run` for runtime apply (needs `sqlcmd`)
- [ ] Look at [Databasecode](https://github.com/nakkavamsi/Databasecode) when unsure about layout or CI
