# sql-migration-tools — Repository and Code Documentation

**Package:** `sql-migration-tools` v1.0.0  
**CLI:** `sql-mig`  
**Python:** 3.10+  
**License:** MIT  
**GitHub:** https://github.com/nakkavamsi/DBDeploymentTool

This package is shared Python tooling for **migration-driven SQL Server database projects** (Databasecode / SSDT-style). It does **not** contain schema SQL. Each database repo keeps its own `Deployments/`, `SchemaModel/`, and `*.sqlproj`. This repo only provides the CLI that creates, stamps, syncs, bootstraps, and applies those scripts.

**Start here for usage:** [HOWTO.md](HOWTO.md).  
**Use from other database repos / Databasecode sample:** [USING-FROM-DATABASE-PROJECTS.md](USING-FROM-DATABASE-PROJECTS.md).  
This file is the architecture and internals reference.

---

## 1. Purpose

Typical SSDT projects treat `SchemaModel/` (declarative `CREATE` scripts) as the source of truth and generate a dacpac. This tooling inverts that for **runtime deployments**:

| Layer | Role |
|-------|------|
| `Deployments/Migrations/` | **Source of truth.** Versioned, incremental SQL that actually runs against databases. |
| `SchemaModel/` | **Generated.** Declarative object scripts for dacpac / SSDT build. Do not edit by hand. |
| `Deployments/pre-deployments/` | Optional one-shot scripts (permissions, linked servers, `master` setup) tracked separately. |
| `Deployments/Rollback/` | Lives in the database project, not this package. |

`sql-mig` keeps those layers consistent:

1. Authors write (or bootstrap) migration files.
2. `sync` rebuilds `SchemaModel/` from every migration in semver order.
3. `run` applies pending migrations to SQL Server via `sqlcmd` and records them in history tables.

## 3. Expected database-project layout

Commands default `--project-root` to the **current working directory**. That directory must look like:

```
MyDatabaseProject/
├── Databasecode.sqlproj          # SSDT project (not in this repo)
├── SchemaModel/                  # generated by sql-mig sync
│   ├── dbo/
│   │   ├── Tables/
│   │   ├── Views/
│   │   ├── StoredProcedures/
│   │   ├── Functions/
│   │   ├── Triggers/
│   │   ├── Synonyms/
│   │   ├── Sequences/
│   │   └── Types/
│   │       ├── UserDefinedTableTypes/
│   │       └── UserDefinedDataTypes/
│   ├── Security/
│   │   ├── Schemas/
│   │   └── Roles/
│   └── Assemblies/
└── Deployments/
    ├── Migrations/
    │   ├── 1.0.0/
    │   │   └── 01_20260522143000_a3f9b2c1_dbo.person.sql
    │   └── 2.3.0/
    │       └── 01_...._dbo.person.add_status.sql
    ├── pre-deployments/          # optional
    └── Rollback/                 # optional, unused by this CLI
```

### Version folders

Migration folders **must** be semantic versions: `MAJOR.MINOR.PATCH`.

- Valid: `1.0.0`, `2.3.0`, `10.0.1`
- Invalid: `1.1`, `v1.0.0`, `1.0.0-beta`

`sync` and `run` exit with an error if any non-hidden subdirectory fails that pattern.

Files inside a version folder are processed in **filename order**. `sql-mig new` prefixes a two-digit sequence (`01_`, `02_`, …) so order is stable.

## 4. CLI architecture

`sql_mig.cli` is a thin dispatcher. It does not use `argparse` subparsers.

```
sql-mig [sync|run|new|stamp|bootstrap] [options]
```

Flow:

1. No args / `-h` / `--help` / `help` → print top-level help, exit 0.
2. Unknown command → stderr error, exit 2.
3. Known command → `__import__` the module and call `module.main()`.
4. `sys.argv` is rewritten to `["sql-mig <command>", ...remaining]` so each module’s own `argparse` sees the right program name.

`python -m sql_mig` is equivalent to `sql-mig`.

| Command | Module | Purpose |
|---------|--------|---------|
| `sync` | `sql_mig.sync` | Rebuild `SchemaModel/` from migrations |
| `run` | `sql_mig.run` | Apply pending scripts via sqlcmd |
| `new` | `sql_mig.new_migration` | Scaffold a stamped migration file |
| `stamp` | `sql_mig.stamp` | Add or normalize `-- Migration-Id` headers |
| `bootstrap` | `sql_mig.bootstrap` | Split a baseline export into migrations |

## 5. Migration identity (`migration_id.py`)

Every migration file is identified by a header, **not** by filename:

```sql
-- Migration-Id: 20260522143000_a3f9b2c1

ALTER TABLE ...
```

### ID format

`generate_migration_id()` returns `YYYYMMDDHHMMSS_<8-hex>`:

- UTC timestamp (`datetime.now(timezone.utc)`)
- First 8 hex chars of a UUID4

That is sortable and unique enough for concurrent authors.

### Header helpers

| Function | Behavior |
|----------|----------|
| `build_migration_header(id)` | `-- Migration-Id: {id}\n\n` |
| `has_migration_id(content)` | True if the header regex matches |
| `extract_migration_id(content)` | Returns the ID or `None` |
| `strip_existing_migration_header(content)` | Drops `Migration-Id`, legacy `Migration-Version`, and `Created-Utc` lines at the top |
| `prepend_migration_header(content, id)` | Strip old header, write a clean one |
| `parse_version_from_path(path)` | Parent folder name if it is semver |
| `next_sequence_number(version_dir)` | Max `NN_` prefix among `*.sql` + 1 |
| `slugify_name(name)` | Keep `[a-zA-Z0-9._-]`, collapse other chars to `_` |

`run` records **Migration-Id** in `dbo.__MigrationHistory`. Renaming a file does not re-apply it; changing the ID would.

## 6. Command reference

### 6.1 `sql-mig new`

Creates a new file under `Deployments/Migrations/{version}/`.

```bash
sql-mig new --version 2.3.0 --name dbo.person.add_status
sql-mig new --version 2.3.0 --name dbo.person.add_status --content "ALTER TABLE ..."
sql-mig new --version 2.3.0 --name dbo.person.add_status --dry-run
```

**Required:** `--version` (semver), `--name` (logical slug).

**Filename:** `{sequence:02d}_{migration_id}_{slug}.sql`

Example:

```
Deployments/Migrations/2.3.0/01_20260522143000_a3f9b2c1_dbo.person.add_status.sql
```

If `--content` is omitted, the body is `-- TODO: add migration SQL`. `--dry-run` prints path and content without writing.

---

### 6.2 `sql-mig stamp`

Ensures migration files have a unique `-- Migration-Id`.

```bash
sql-mig stamp path/to/file.sql
sql-mig stamp --all
sql-mig stamp --all --refresh
sql-mig stamp --all --quiet
```

| Flag | Meaning |
|------|---------|
| `paths` | Specific `.sql` files |
| `--all` | Every `Deployments/Migrations/*/*.sql` |
| `--refresh` | Keep existing ID, rewrite header (drop legacy version/created lines) |
| `--quiet` | Only print when a file changes |

Files whose path does not contain `Deployments/Migrations` and end in `.sql` are skipped.

`sync` also auto-stamps missing IDs (`ensure_migration_ids`) so files created by hand still get an ID before schema generation.

---

### 6.3 `sql-mig sync`

Rebuilds `SchemaModel/` from all migrations. This is the core of the package (`sync.py`, ~1600 lines).

```bash
sql-mig sync
sql-mig sync --project-root /path/to/db-project
```

**Pipeline:**

1. Require `Deployments/Migrations/`.
2. Stamp any `.sql` missing a Migration-Id.
3. Validate version folders; sort by `(major, minor, patch)`, then filename.
4. Walk each file and accumulate:
   - **Tables** in `TableModel` (CREATE + ALTER + indexes + statistics)
   - **Roles** in `RoleModel` (CREATE ROLE + members)
   - **Other objects** as last-write-wins SQL keyed by output path
5. Write declarative scripts with a generated header.
6. Delete stale leftover folders: `**/Tables/Indexes`, `Security/RoleMemberships`, `**/Maintenance`.

Later versions **overwrite** earlier definitions for the same object. `ALTER TABLE` is applied incrementally onto the in-memory table model.

Generated files start with:

```sql
-- AUTO-GENERATED from Deployments/Migrations/. Do not edit directly.
-- Add or change scripts under Deployments/Migrations/MAJOR.MINOR.PATCH/ and rebuild.
```

`CREATE OR ALTER` is rewritten to `CREATE`. `IF OBJECT_ID ... BEGIN ... END` wrappers are unwrapped. `GO` batches are preserved where SSDT needs them (table + indexes, role + members).

### 6.4 `sql-mig run`

Applies scripts to a live SQL Server using `sqlcmd`.

```bash
sql-mig run -S localhost -d MyDb -U sa -P 'secret' -C
sql-mig run -S localhost -d MyDb -E -C --status
sql-mig run -S localhost -d MyDb -U sa -C --pre-deployments
sql-mig run --list-files
sql-mig run --dry-run -S localhost -d MyDb -U sa -C
```

**Connection (required unless listing files):**

| Flag | sqlcmd | Meaning |
|------|--------|---------|
| `-S` / `--server` | `-S` | Instance |
| `-d` / `--database` | `-d` | Target database |
| `-U` / `--user` | `-U` | SQL login |
| `-P` / `--password` | `-P` | Password |
| `-E` / `--trusted` | `-E` | Windows / integrated auth |
| `-C` / `--trust-server-cert` | `-C` | Trust server cert |
| `--sqlcmd` | | Path to executable (default `sqlcmd`) |
| `--sqlcmd-arg ARG` | | Extra args, repeatable |

**Selection:**

| Flag | Meaning |
|------|---------|
| `--pre-deployments` | Run pending pre-deploy scripts, then migrations |
| `--pre-deployments-only` | Pre-deploy only |
| `--exclude-version X.Y.Z` | Skip a version folder (repeatable) |
| `--up-to-version X.Y.Z` | Include versions `<=` this |
| `--list-files` | Print migrations in order (no DB) |
| `--list-pre-deployments` | Print pre-deploy files (no DB) |
| `--status` | Applied vs pending, then exit |
| `--dry-run` | Show pending, do not execute |

Missing `sqlcmd` on PATH → exit 1. Missing Migration-Id or duplicate IDs → error telling you to run `sync` or `stamp --all`.

Execution is **not transactional across files**. If script N fails, N is not recorded; earlier scripts stay applied. Fix the script and re-run.

### 6.5 `sql-mig bootstrap`

Turns a schema-only baseline export (SSMS Generate Scripts, SqlPackage, mssql-scripter) into one migration file per object.

```bash
sql-mig bootstrap --input baseline.sql --version 1.0.0
sql-mig bootstrap --input baseline.sql --version 1.0.0 --sync
sql-mig bootstrap --input baseline.sql --version 1.0.0 --dry-run
sql-mig bootstrap --input baseline.sql --version 1.0.0 --force
```

**Behavior:**

1. Strip block comments, `USE [db]`, and session `SET` noise.
2. Parse objects using the same extractors as `sync`.
3. Wrap idempotent guards (`IF OBJECT_ID IS NULL`, `IF SCHEMA_ID IS NULL`, `CREATE OR ALTER` for routines/types).
4. Peel foreign keys out of `CREATE TABLE` into later `ALTER TABLE ... ADD CONSTRAINT` files so tables can be created in dependency order.
5. Topologically sort tables by FK graph; warn and keep original order on cycles.
6. Write `{seq:02d}_{slug}.sql` with a Migration-Id.
7. Warn about unrecognized `GO` batches (skipped).
8. Optionally `--sync` SchemaModel.

`--force` deletes existing `.sql` in that version folder first. Without `--force`, a non-empty folder is an error.

Object write order (`KIND_ORDER`):

1. schema → 2. type → 3. sequence → 4. assembly → 5. table → 6. alter_table → 7. index → 8. statistics → 9. routine → 10. synonym → 11. role → 12. role_membership

## 7. Schema sync internals

### 7.1 `TableModel`

In-memory representation of one table, accumulated across versions.

| Field | Contents |
|-------|----------|
| `columns` | name → full column definition |
| `constraints` | name → constraint SQL |
| `constraint_order` | insertion order |
| `indexes` | name → `CREATE INDEX` SQL |
| `index_order` | insertion order |
| `statistics` | name → `CREATE STATISTICS` SQL |
| `statistics_order` | insertion order |

**Mutations:**

- `load_from_create` — parse `CREATE TABLE (...)`, reset columns/constraints/indexes/stats
- `apply_add` — add column, named constraint, inline PK/FK/UNIQUE/CHECK, or `DEFAULT ... FOR col`
- `apply_drop` — `DROP COLUMN` / `DROP CONSTRAINT`
- `apply_alter_column` — replace column definition
- `add_index` / `drop_index`
- `add_statistic` / `drop_statistic`

`render()` emits:

```sql
CREATE TABLE [schema].[name] (
    ...
);
GO

CREATE INDEX ...
GO

CREATE STATISTICS ...
```

SSDT requires `GO` between statements in a single table file.

Default constraints written as `ALTER TABLE ... ADD CONSTRAINT ... DEFAULT ... FOR [col]` are merged **onto the column line**, not as table-level constraints.

### 7.2 `RoleModel`

- `create_sql` — `CREATE ROLE`
- `members` — member name → `ALTER ROLE [role] ADD MEMBER [member];`

`sp_addrolemember` and `EXEC(N'...')` forms are normalized to `ALTER ROLE`. If membership exists without a CREATE, a `CREATE ROLE` is synthesized.

### 7.3 SQL extraction

`sync.py` uses regex plus parenthesis-depth scanners (not a full T-SQL parser). It understands:

| Construct | Handling |
|-----------|----------|
| `CREATE TABLE` (optional `IF OBJECT_ID` / `SCHEMA-OBJECT` block) | Table model |
| `ALTER TABLE ... ADD/DROP/ALTER` | Merged into table model |
| `CREATE INDEX` / `DROP INDEX` | Merged into parent table file |
| `CREATE STATISTICS` / `DROP STATISTICS` | Merged into parent table file |
| `CREATE [OR ALTER] PROCEDURE/VIEW/FUNCTION/TRIGGER` | Last definition wins; `BEGIN/END` depth for body end |
| `CREATE SYNONYM` | Synonyms folder |
| `CREATE TYPE ... FROM` / `AS TABLE` | `Types/UserDefinedDataTypes` or `UserDefinedTableTypes` |
| `CREATE SCHEMA` | `Security/Schemas` |
| `CREATE ROLE` | Role model |
| `ALTER ROLE ADD MEMBER` / `sp_addrolemember` | Role model |
| `CREATE SEQUENCE` | `{schema}/Sequences` |
| `CREATE ASSEMBLY` | `Assemblies/` |
| `-- SCHEMA-OBJECT-START` / `-- SCHEMA-OBJECT-END` | Explicit full desired definition |

Identifiers may be `[bracketed]` or unquoted `\w+`.

### 7.4 SchemaModel output map

| Object | Path |
|--------|------|
| Table | `SchemaModel/{schema}/Tables/{name}.sql` |
| Procedure | `SchemaModel/{schema}/StoredProcedures/{name}.sql` |
| View | `SchemaModel/{schema}/Views/{name}.sql` |
| Function | `SchemaModel/{schema}/Functions/{name}.sql` |
| Trigger | `SchemaModel/{schema}/Triggers/{name}.sql` |
| Synonym | `SchemaModel/{schema}/Synonyms/{name}.sql` |
| Sequence | `SchemaModel/{schema}/Sequences/{name}.sql` |
| Table type | `SchemaModel/{schema}/Types/UserDefinedTableTypes/{name}.sql` |
| Alias type | `SchemaModel/{schema}/Types/UserDefinedDataTypes/{name}.sql` |
| Schema | `SchemaModel/Security/Schemas/{schema}.sql` |
| Role | `SchemaModel/Security/Roles/{role}.sql` |
| Assembly | `SchemaModel/Assemblies/{assembly}.sql` |

## 8. Runtime history tables

Created automatically on first `sql-mig run` (or `--status`).

### `dbo.__MigrationHistory`

| Column | Type | Notes |
|--------|------|-------|
| `MigrationId` | `NVARCHAR(64)` PK | From `-- Migration-Id` |
| `VersionFolder` | `NVARCHAR(20)` | e.g. `2.3.0` |
| `ScriptName` | `NVARCHAR(260)` | Filename only |
| `AppliedUtc` | `DATETIME2(7)` | Default `SYSUTCDATETIME()` |

Pending = files on disk whose ID is not in this table.

### `dbo.__PreDeploymentHistory`

| Column | Type | Notes |
|--------|------|-------|
| `ScriptPath` | `NVARCHAR(500)` PK | Path relative to `pre-deployments/` |
| `AppliedUtc` | `DATETIME2(7)` | Default `SYSUTCDATETIME()` |

Pre-deploy scripts may include:

```sql
-- SqlCmd-Database: master
```

That script runs against `master` (or whatever name is given). History is recorded **in that database**, not necessarily the `-d` target.

## 9. `SqlCmdRunner` (`run.py`)

Wraps `subprocess.run` around `sqlcmd`:

- `run_query(sql)` → `sqlcmd -b -Q "..."`
- `run_file(path)` → `sqlcmd -b -i file.sql`
- `-b` aborts on error (non-zero exit)

Stdout from `SELECT MigrationId` is parsed line-by-line, skipping header rows (`MigrationId`, dashed underlines).

SQL literals in `INSERT` statements are escaped by doubling single quotes.

## 10. Typical workflows

### New change in an existing project

```bash
cd MyDatabaseProject
sql-mig new --version 2.3.0 --name dbo.person.add_status
# edit the generated SQL
sql-mig sync
dotnet build Databasecode.sqlproj
sql-mig run -S localhost -d MyDb -U sa -C --status
sql-mig run -S localhost -d MyDb -U sa -C
```

### Adopt an existing database

```bash
# export schema-only SQL from SSMS / SqlPackage
sql-mig bootstrap --input baseline.sql --version 1.0.0 --sync
sql-mig run -S localhost -d MyDb -U sa -C --dry-run
```

If the database already matches the baseline, either skip applying `1.0.0` (`--exclude-version 1.0.0`) or stamp history another way; this CLI does not have a “mark as applied without running” command.

### CI

```yaml
- run: pip install "sql-migration-tools @ git+https://github.com/nakkavamsi/DBDeploymentTool.git"
- run: sql-mig sync
- run: sql-mig run -S ${{ env.SQL_HOST }} -d MyDb -U sa -P "$SQL_PASSWORD" -C
```

MSBuild:

```xml
<Exec Command="sql-mig sync" WorkingDirectory="$(MSBuildProjectDirectory)" />
```

## 12. Conventions and limitations

**Conventions**

- Migrations are the source of truth; SchemaModel is generated.
- One logical change per file is recommended; filenames are documentation, IDs are identity.
- Use `CREATE OR ALTER` in migrations for routines; sync strips `OR ALTER` for SSDT.
- Prefer idempotent guards in bootstrap-generated files so re-runs on empty DBs are safe; later incremental migrations usually are not wrapped.

**Parser limits**

- Regex/scanner, not a T-SQL grammar. Unusual quoting, dynamic SQL, or nested comments can confuse extractors.
- `ALTER TABLE` must end with `;` for the regex to match.
- Routine bodies are bounded by matching `BEGIN`/`END` after `AS`; nested procedures or atypical bodies may truncate.
- `DROP TABLE` / `DROP PROCEDURE` are not modeled; later CREATE overwrites the SchemaModel file, but dropped objects are not deleted from SchemaModel automatically except the stale-folder cleanup listed above.
- No rollback command; `Deployments/Rollback/` is unused by this CLI.

**Runtime limits**

- Requires `sqlcmd`.
- No distributed transaction around “run file + insert history”. A crash after a successful script and before `INSERT` can cause a re-run of that script.
- History SELECT parsing assumes default sqlcmd tabular output.
